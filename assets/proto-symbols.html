这里最关键的一条，上面表格第三行后半句： OpenMoji 只是"换一套画法"，正文里存的仍然是 🚀 这个码位。 也就是说 —— 用户把文档发给别人、用别的编辑器打开，看到的还是彩色 emoji，不是我们的描边版。 想让它"到哪都是描边样"，只能存 :rocket: 这种短码 + 自己渲染， 但那样纯文本编辑器里就是一堆短码，反而更脏。
我的判断（要你拍板）：正文那一层只能用 Unicode 字符，不要试图用图片。 因为"能插进文本"这个要求的本质是可移植：这份 .md 要能在 VS Code、GitHub、手机上打开还成立。 SVG 做不到这件事，只有字符能。 所以真正的选择不是"用哪套图标"，而是"面板里放哪些字符、怎么分类、能不能搜"。

那"另一套符号集"到底指什么 三种理解，做法完全不同

理解要做什么代价
A 给用户一个符号面板按类目整理几百个 Unicode 字符 + 搜索 + 最近使用；点一下插进正文纯前端，一个数据文件
B 让用户换文件夹图标`.dusk/icons.json` 存"路径 → 字符"；树里 16px 渲染；同面板供选择一个小配置层，可删可重建
C 引入一整套图形符号库再打包一套 SVG（OpenMoji / Material Symbols / 自定义），供图标选择器用包体 + 协议 + 描边风格要重调
这三件不冲突，但顺序有讲究：A 和 B 是"让用户能用"，C 是"更好看"。先做 A+B 就能用起来；C 可以后加，而且加了不影响前两步存下的数据 —— 因为存的是字符，不是图片。
